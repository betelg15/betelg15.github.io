배경: 왜 하필 Stable Fluids인가

풀어야 할 방정식

비압축성(incompressible) 유체의 속도장 u와 압력 p는 Navier–Stokes 방정식을 따릅니다. (블로그가 수식 렌더링을 지원하지 않아 텍스트로 적습니다. 밀도 ρ는 1로 둡니다.)

∂u/∂t = −(u·∇)u  −  ∇p  +  ν∇²u  +  F      (운동량: 이류 / 압력 / 점성 확산 / 외력)
∇·u   = 0                                   (비압축성: 어디서도 유체가 생기거나 사라지지 않음)

화면을 격자로 보고 픽셀 하나를 셀 하나로 두면(Eulerian 관점), GPU의 텍스처가 곧 "격자 배열"이 되고 프래그먼트 셰이더가 "모든 셀에 대해 같은 계산을 하는 루프 본문"이 됩니다. GPU Gems 38장이 정확히 이 비유(Textures = Arrays, Loop Bodies = Fragment Programs)로 설명합니다.

문제는 "폭발"

Stam 이전의 그래픽스용 유체 솔버(예: Foster & Metaxas)는 이 방정식을 명시적(explicit) 시간 적분으로 풀었습니다. 구현은 쉽지만, 시간 간격 dt가 크거나 속도가 빠르면 수치적으로 "blow up"해 버립니다. 사용자가 마우스를 세게 휘두르는 인터랙티브 환경에서는 치명적이죠. Stam은 논문 결론에서 원래 Foster & Metaxas의 방법을 쓰려다 "the instabilities inherent in their method forced us to develop a new algorithm" 이라고 적었습니다.

Stam의 제안은 어떤 dt를 써도 폭발하지 않는(unconditionally stable) 솔버였고, 대신 그는 발표 자료에 스스로 "NOT accurate" 라고 적었습니다. 그래픽스에서는 정확도보다 "보기에 유체 같고, 실시간으로 돌고, 절대 터지지 않는 것"이 중요하다는 판단입니다.

Stable Fluids 한 스텝 해부

핵심은 연산자 분할(operator splitting): 방정식의 항을 한꺼번에 풀지 않고, 하나씩 순서대로 적용합니다. Stam 논문의 순서는 다음과 같습니다.

w0 = u(t)
w1 = w0 + dt·F                  ① 외력 추가
w2 = w1(p(x, −dt))              ② 이류 (semi-Lagrangian 역추적)
w3 = (I − ν·dt·∇²)⁻¹ w2         ③ 점성 확산 (암시적 풀이)
u(t+dt) = P(w3)                 ④ 투영 (발산 제거)

① 외력

마우스 드래그 같은 힘을 속도에 더합니다. GPU Gems는 클릭 위치에 2차원 가우시안 "splat"을 찍어 속도 텍스처에 더하는 방식을 씁니다.

② 이류: 앞으로 밀지 말고, 뒤로 따라가라

"속도가 속도 자신을 실어 나르는" 비선형 항 −(u·∇)u가 가장 까다롭습니다. Stam은 이를 특성곡선법(method of characteristics) 으로 풉니다. 직관적으로는:

각 셀 x에서 현재 속도를 따라 시간을 dt만큼 거꾸로 추적해 출발점 x − dt·u(x)를 찾고, 그 위치의 값을 선형 보간으로 읽어 와 새 값으로 쓴다.

이른바 semi-Lagrangian 이류입니다. GPU에 특히 잘 맞는 이유도 GPU Gems가 정확히 짚습니다. 입자를 앞으로 미는(scatter) 방식은 프래그먼트가 자기가 쓸 위치를 바꿀 수 없기 때문에 셰이더로 구현할 수 없지만, 뒤로 따라가 읽는(gather) 방식은 텍스처 샘플 한 번이면 됩니다.

왜 무조건 안정한가? Stam의 설명은 한 줄입니다. 새 값은 이전 필드의 어떤 지점을 보간한 값이므로, "the maximum value of the new field is never larger than the largest value of the previous field." 선형 보간은 주변 값의 볼록 결합(가중 평균)이라 최댓값을 넘을 수 없고, 따라서 dt가 아무리 커도 값이 증폭되지 않습니다. 참고로 Stam은 고차 보간을 쓰지 않은 이유로 진동·오버슈트에 의한 불안정을 들었습니다.

다음은 제가 직접 쓴 설명용 GLSL입니다(WebGL1 스타일, 실제 프로젝트 코드 아님).

// [설명용 예제] semi-Lagrangian advection
precision highp float;
uniform sampler2D uVelocity;   // 속도장 (xy)
uniform sampler2D uSource;     // 실어 나를 값 (속도 자신, 염료, 높이 등)
uniform vec2  uTexelSize;      // 1.0 / 격자 해상도
uniform float uDt;
varying vec2 vUv;

void main() {
  vec2 vel = texture2D(uVelocity, vUv).xy;
  // 속도를 '격자 셀/초' 단위로 두고, UV 공간으로 바꿔 거꾸로 추적
  vec2 prevUv = vUv - uDt * vel * uTexelSize;
  // LINEAR 필터링된 float 텍스처면 샘플러가 쌍선형 보간을 해 준다
  gl_FragColor = texture2D(uSource, prevUv);
}

③ 점성 확산: 암시적으로

∂u/∂t = ν∇²u를 명시적으로 풀면 점성이 클 때 불안정해지므로, Stam은 암시적(implicit) 형태 (I − ν·dt·∇²) w3 = w2를 씁니다. 이산화하면 희소 선형 시스템이 됩니다. 실무 팁: mofu의 이전 글은 시각 효과라면 이 단계를 생략해도 무방하다고 하며, 실제로 공개 저장소 mnmxmx/fluid-three의 기본 설정도 isViscous: false입니다.

④ 투영: Helmholtz–Hodge 분해

①~③을 거친 w3는 일반적으로 발산(∇·w ≠ 0)이 있어, 유체가 어딘가에서 생기거나 사라지는 상태입니다. 여기서 Helmholtz–Hodge 분해가 등장합니다. 어떤 벡터장이든 발산 없는 장 + 스칼라장의 기울기로 유일하게 분해된다는 정리입니다.

w = u + ∇p          (∇·u = 0)
→ 양변에 발산:  ∇²p = ∇·w      ← 압력 푸아송 방정식
→ 투영:         u = w − ∇p

즉 "발산을 계산 → 푸아송 방정식으로 p를 구함 → 기울기를 빼기" 세 패스입니다. 이 투영 덕분에 유체가 비압축성을 유지하고, Stam의 표현으로는 "the projection step forces the fields to have vortices which result in more swirling-like motions" — 유체 특유의 소용돌이가 생깁니다.

GPU에서 푸아송 방정식 풀기: Jacobi 반복

GPU Gems 38장은 이 푸아송 방정식을 Jacobi 반복으로 풉니다. 각 셀을 "이웃 네 칸의 평균 − 우변"으로 갱신하는 걸 수십 번 반복하는, 가장 단순한 방법입니다. 모든 셀이 이전 반복 결과만 읽으므로 완전히 병렬이고, 텍스처 두 장을 번갈아 쓰는 ping-pong으로 구현됩니다. 챕터는 압력에 대해 보통 40~80회를 쓰고, 20회 미만이면 오차가 눈에 띈다고 권합니다.

// [설명용 예제] 압력 푸아송 방정식 ∇²p = div 의 Jacobi 한 스텝 (셀 간격 h = 1)
precision highp float;
uniform sampler2D uPressure;     // 이전 반복의 p (ping)
uniform sampler2D uDivergence;   // ∇·w
uniform vec2 uTexelSize;
varying vec2 vUv;

void main() {
  float pL = texture2D(uPressure, vUv - vec2(uTexelSize.x, 0.0)).r;
  float pR = texture2D(uPressure, vUv + vec2(uTexelSize.x, 0.0)).r;
  float pB = texture2D(uPressure, vUv - vec2(0.0, uTexelSize.y)).r;
  float pT = texture2D(uPressure, vUv + vec2(0.0, uTexelSize.y)).r;
  float div = texture2D(uDivergence, vUv).r;
  // (pL + pR + pB + pT − 4p) = div  →  p = (pL + pR + pB + pT − div) / 4
  gl_FragColor = vec4((pL + pR + pB + pT - div) * 0.25, 0.0, 0.0, 1.0);
}

// [설명용 예제] three.js에서 ping-pong으로 반복 (렌더 타깃 두 개를 번갈아 사용)
for (let i = 0; i < 40; i++) {
  jacobiMaterial.uniforms.uPressure.value = rtA.texture;  // 읽기
  renderer.setRenderTarget(rtB);                          // 쓰기
  renderer.render(fullscreenQuadScene, camera);
  [rtA, rtB] = [rtB, rtA];                                // 교체
}
renderer.setRenderTarget(null);

⚠️ 흔한 오해: "Stable Fluids = Jacobi 반복"은 아닙니다. Stam의 원 논문은 오히려 "Relaxation schemes, though, have poor convergence and usually require many iterations" 라며 더 정확한 솔버를 택했습니다. 이론적 최선은 multigrid, 실제 구현은 FISHPAK 라이브러리 솔버였고, 주기 경계에서는 FFT로 확산과 투영을 푸리에 공간에서 한 번에 처리합니다. Jacobi는 GPU Gems가 "simplicity and easy implementation" 때문에 고른 것이고, 지금 웹에 돌아다니는 WebGL 유체 구현 대부분이 이 GPU Gems 계보입니다.

손으로 확인해 보기

위 이야기를 작은 Node.js 장난감으로 확인했습니다. (논문·저자 코드가 아니라 제가 쓴 64×64 주기 경계 CPU 예제입니다. 전체 파일: stable_fluids_toy.mjs, node stable_fluids_toy.mjs로 실행)

핵심 부분만 발췌하면 이렇습니다.

// semi-Lagrangian: 거꾸로 따라가서 보간해 읽기
out[k] = sample(q, i - dt * u[k], j - dt * v[k]);

// 비교용 명시적(FTCS) 이류: 중앙차분 기울기로 앞으로 적분
out[k] = q[k] - dt * (u[k] * dqdx + v[k] * dqdy);

제 환경(Node.js v20)에서의 출력입니다.

[안정성] 염료 최댓값 |q|max (초기 1.0), 30 스텝 후
  dt= 0.5  semi-Lagrangian=1.000  explicit=9.86e+0
  dt=   5  semi-Lagrangian=1.000  explicit=8.85e+21
  dt=  50  semi-Lagrangian=0.368  explicit=6.15e+51

명시적 방법은 dt=0.5에서도 값이 10배 가까이 부풀고, dt를 키우면 그대로 폭발합니다. semi-Lagrangian은 어떤 dt에서도 1.0을 넘지 않습니다. 그런데 dt=50에서는 최댓값이 0.368로 줄어든 것에 주목하세요. 터지지 않는 대신 보간을 반복하며 값이 뭉개지는 수치 확산(numerical dissipation) 입니다. "안정하다"는 "정확하다"가 아닙니다 — Stam이 "NOT accurate"라고 쓴 바로 그 지점이죠. GPU Gems도 데모에서 염료 확산 항을 아예 계산하지 않는데, 이류의 수치 오차가 어차피 확산을 만들어 내기 때문이라고 설명합니다.

투영 쪽도 하나 확인했습니다. 발산이 있는 랜덤 "마우스 힘" 속도장을 투영한 뒤 남는 발산(중앙차분 기준 RMS)입니다.

[투영] Jacobi 반복 수에 따른 잔여 발산 RMS (투영 전: 0.0883)
  iters=  0  stride1=0.0883  stride2=0.0883
  iters= 20  stride1=0.0475  stride2=0.0182
  iters= 80  stride1=0.0282  stride2=0.0059
  iters=400  stride1=0.0216  stride2=0.0002
  • 반복 수가 곧 품질 손잡이입니다. 20회에서는 발산이 아직 절반 가까이 남습니다. GPU Gems가 "20회 미만은 오차가 눈에 띈다"고 한 이유를 숫자로 볼 수 있습니다.
  • stride1은 위 GLSL처럼 바로 옆 칸을 쓰는 라플라시안, stride2는 두 칸 건너 셀을 쓰는 라플라시안입니다. 셀 중심에 속도와 압력을 함께 두는 격자(collocated grid)에서 발산과 기울기를 중앙차분으로 계산하면, 그 둘을 합성한 라플라시안은 정확히 2칸 간격 스텐실이 됩니다. 그래서 stride2는 (이 장난감에서) 반복할수록 발산이 0으로 수렴하고, stride1은 일정 수준에서 멈춥니다. 대신 2칸 스텐실은 격자를 서로 연결되지 않은 부분 격자로 쪼개 체커보드 형태의 압력 잡음이 생길 수 있다는 단점이 알려져 있어, 더 정확하게 가려면 GPU Gems 38.5.3이 소개하는 staggered grid로 갑니다. 흥미롭게도 mofu의 이전 글과 fluid-three의 poisson.frag는 수식을 손으로 전개해 이 2칸 스텐실에 도달했습니다.

mofu 글은 Stable Fluids를 어떻게 "액체"로 바꿨나

여기서부터가 원문의 핵심입니다. 먼저 짚어 둘 사실: Stable Fluids 자체는 물 같은 액체의 표면을 다루지 않습니다. Stam은 결론에서 "we have not addressed the problem of simulating fluids with free boundaries, such as water" 라고 명시했고, GPU Gems 38장도 자유 표면(free surface)은 범위 밖이라고 적습니다. 두 방법 모두 "화면 전체를 채운 유체"의 속도장만 계산합니다.

mofu의 해법은 속도장은 Stable Fluids에게 맡기고, 액체의 '양'은 별도의 높이맵으로 표현하는 것입니다. 이전 글 Stable Fluids with three.js(2022-07-31)의 시뮬레이션이 만든 velocity map을 그대로 쓰고, 그 위에 세 단계를 얹습니다.

  1. 높이맵(두께) 이동 — FBO의 R 채널에 액체 두께를 저장합니다. 초기값은 셰이더로 만든 반구형 방울. 매 프레임 각 픽셀은 - 자기 속도가 클수록 두께의 일부(removed)를 잃고, - 속도를 거꾸로 추적한 출발 지점(semi-Lagrangian과 같은 backtraceUv())에서 두께의 일부(added)를 가져옵니다. - smoothstep으로 속도 임계값을 둬서, 거의 안 움직이는 곳은 흐르지 않게 합니다.
  2. 알파맵으로 자국 남기기 — 지금까지 기록된 두께의 최댓값 이력을 저장해, 액체가 지나간 자리에 얇게 색이 남도록 합니다. 저자는 이것이 건조·흡수의 물리 모델이 아니라 "단순한 이력"이라고 밝힙니다.
  3. 높이맵에서 법선 계산 → Matcap 렌더링 — 지오메트리를 변형하지 않고, 프래그먼트 셰이더에서 이웃 픽셀 높이로 두 접선 벡터를 만들어 외적으로 법선을 구한 뒤 Matcap 텍스처로 하이라이트를 입힙니다.

1단계의 구조를 제 식으로 단순화하면 이렇습니다(설명용 의사 코드, 원문 코드 아님. 원문의 상수와 세부 구현은 원문 참고).

// [설명용 예제] '속도에 비례해 내보내고, 역추적한 곳에서 받아 오는' 두께 갱신
float h      = texture2D(uHeight, vUv).r;
vec2  vel    = texture2D(uVelocity, vUv).xy;
vec2  srcUv  = vUv - uDt * vel * uTexelSize;                // semi-Lagrangian 역추적
float hSrc   = texture2D(uHeight, srcUv).r;
float kHere  = smoothstep(uMinSpeed, uMaxSpeed, length(vel));
float kSrc   = smoothstep(uMinSpeed, uMaxSpeed, length(texture2D(uVelocity, srcUv).xy));
float removed = min(h,    kHere * uRate * h);
float added   = min(hSrc, kSrc  * uRate * hSrc);
gl_FragColor  = vec4(max(0.0, h - removed + added), 0.0, 0.0, 1.0);

"물리적으로 정확하지 않다"는 고백이 핵심이다

저자는 이 방식이 부피를 보존하지 않는다고 분명히 씁니다. 이유는 앞의 GPU 제약과 같습니다. 프래그먼트는 다른 픽셀에 값을 써 넣을(scatter) 수 없으니, 각 목적지 픽셀이 출발지를 거꾸로 찾아 읽어(gather) 옵니다. 그런데 여러 픽셀이 대략 같은 출발 영역을 읽을 수 있어서, 빠져나간 양과 들어온 양의 합이 맞지 않습니다. 원문 데모에서 직선으로 끌면 꽤 안정적이지만, 원을 그리면 샘플링 편향이 누적돼 액체가 계속 늘어난다고 합니다. 저자는 이를 알고도 "보기 좋은 것"을 택했습니다.

덤: 8비트 텍스처의 계단

원문에는 높이맵을 8비트와 32비트 float 텍스처로 토글해 보는 데모도 있습니다. 8비트는 채널당 256단계뿐이라 높이가 양자화되고, 법선은 높이의 차분에서 나오므로 그 계단이 셰이딩에 그대로 드러납니다. 색 그라데이션의 밴딩 문제로만 알던 정밀도 한계가 "조명 계단"으로 보인다는 관찰입니다. 실무 교훈: 시뮬레이션용 FBO는 THREE.FloatType(또는 HalfFloatType) 렌더 타깃을 쓰세요. 원문 저자의 이전 글 코드도 FBO를 FloatType으로 만듭니다.

마지막 실험으로 색이 다른 세 방울을 같은 속도장 위에서 섞는 데모도 있는데, 저자는 두께에 따른 색 혼합에 단순화한 Kubelka–Munk 모델을 썼다고 설명합니다.

개발자로서 가져갈 점

  1. "무조건 안정"은 인터랙티브 그래픽스의 1순위 요구사항이다. 사용자가 어떤 입력을 주든 터지지 않는 대신, 정확도와 에너지(수치 확산)를 내준다. 이 트레이드오프를 알고 쓰자.
  2. GPU에서는 scatter 대신 gather로 생각하라. semi-Lagrangian 이류도, mofu의 두께 이동도 "목적지에서 출발지를 거꾸로 찾아 읽는" 구조다. 그 대가(보존량이 깨짐)도 함께 이해해야 한다.
  3. Jacobi 반복 수는 품질 손잡이다. 20회 미만은 눈에 띄는 오차, 40~80회가 GPU Gems의 권장. 성능 예산에 맞춰 조절하자.
  4. 시뮬레이션 FBO는 float로. 8비트에서는 시뮬레이션 값이 아니라 그 미분(법선)에서 먼저 티가 난다.
  5. 물리는 재료, 목표는 '보이는 것'. 정확한 액체 시뮬레이션 없이도, 속도장 하나 + 높이맵 + 이력 + Matcap으로 "펴 바르는 파운데이션"을 만들 수 있다.
