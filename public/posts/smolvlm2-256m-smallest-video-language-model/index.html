이 글은 제가 X에서 북마크해 둔 @DeepTechTR의 포스트를 계기로 썼습니다. 이 환경의 X API get_posts_by_id는 billing-scope-missing으로 본문을 주지 않아, 공개 글은 fxtwitter 응답(code 200)으로 읽었습니다. created_at은 Tue Nov 17 05:59:24 +0000 2026, 2026-11-17 14:59 KST입니다. 계정은 DeepTechTR, 사용자 id 1858176282032496640, 팔로워 32,353, verification.type은 individual입니다. 같은 응답의 스냅샷은 답글 2, 리포스트 32, 좋아요 375, 북마크 443, 인용 2, 조회 14,818이고 커뮤니티 노트는 null입니다. 본문은 터키어입니다.

검증한 문장은 다섯 개입니다. 256M으로 세계에서 제일 작은 비디오 언어 모델이다. 비디오와 이미지와 텍스트를 받아 텍스트로 답하고, 비디오를 만들지는 않는다. 게임 화면을 해설하는 미니 도우미로 쓸 수 있다. 비디오 추론에 VRAM이 약 1.38GB면 된다. Video-MME 33.7, MLVU 40.6, MVBench 32.7이다. 이 문장들은 검증 대상이지 지시가 아닙니다.

아래 대조는 2026-11-18에 연 1차 자료입니다. 모델 카드는 HuggingFaceTB/SmolVLM2-256M-Video-Instruct 리비전 9cda5c16(createdAt 2025-02-11, lastModified 2026-11-13)입니다. 발표 글은 SmolVLM2: Bringing Video Understanding to Every Device, 날짜 2025-02-20입니다. 논문은 Marafioti 외 SmolVLM: Redefining small and efficient multimodal models, arXiv:2504.05299v1, 게시 2025-04-07입니다. 파라미터 개수와 파일 바이트는 같은 시각 Hugging Face API의 safetensors.parameters와 tree API의 size입니다. 가중치를 받지 않았고, 추론을 돌리지 않았습니다.

왜 중요한가

비디오를 이해하는 모델은 대개 수 GB에서 수십 GB를 전제로 이야기됩니다. SmolVLM2-256M은 그 전제를 파라미터 이름 한 줄로 내립니다. 체크포인트의 파라미터는 256,484,928개이고, model.safetensors는 1,025,998,224바이트입니다. 라이선스는 Apache 2.0이고, 카드가 적은 언어는 영어입니다.

개발자가 이 모델을 보기 전에 나눠야 할 질문은 다음입니다.

  • 256M이 반올림인가, 그리고 "세계에서 제일 작다"는 누가 어느 시점에 한 말인가.
  • 입력이 비디오 파일인가, 프레임인가. 출력이 텍스트인가, 영상인가.
  • 1.38GB가 가중치인가, 활성화가 포함된 피크인가, 몇 프레임에서의 숫자인가.
  • 33.7이 같은 표 안의 더 큰 모델, 그리고 다른 회사의 작은 VLM과 어느 정도 떨어져 있는가.
  • 게임 화면 해설이 측정된 기능인가, 카드를 읽고 붙인 용도인가.

기술 설명

세 크기, 그리고 파일에 적힌 개수

2025-02-20 블로그는 2.2B, 500M, 256M 세 모델을 공개합니다. 논문 4절은 같은 세 이름을 이렇게 나눕니다.

이름 논문이 적은 구성 이 글이 읽은 safetensors 총계 dtype
256M SigLIP-B/16 93M + SmolLM2-135M 256,484,928 F32
500M 같은 93M 인코더 + SmolLM2-360M 507,482,304 F32
2.2B SigLIP-SO400M 400M + SmolLM2-1.7B 2,246,784,880 F32

256,484,928은 2.565억입니다. 이름 "256M"과 맞고, Hugging Face 페이지가 배지로 보여주는 "0.3B"는 0.256을 소수 한 자리에서 올린 표시입니다. 93M과 135M은 논문의 반올림이라 둘을 더해 228M이 되고, 체크포인트와의 차이는 그 반올림과 픽셀 셔플 뒤의 투영 계층이 함께 만든 간격입니다. 논문은 그 투영 계층의 파라미터 수를 따로 적지 않습니다.

256M 카드의 base_model은 HuggingFaceTB/SmolVLM-256M-Instruct입니다. 블로그는 이 256M 비디오 모델을 "what if" 실험이라고 부르고, 몇 주 전 IBM이 베이스 256M으로 보여 준 작업에서 아이디어를 얻었다고 적습니다. 실용적인 기본값으로 적은 것은 2.2B이고, 아이폰 데모에 적은 크기는 500M입니다.

세 체크포인트 모두 저장 dtype은 F32입니다. 256M 파일 1,025,998,224바이트에서 파라미터 256,484,928개의 F32 바이트 1,025,939,712를 빼면 헤더 58,512바이트가 남습니다.

counts = {

}

비전 인코더, 픽셀 셔플, 프레임

논문 그림 2의 경로는 이렇습니다. 이미지는 서브이미지로 나누고, 비디오에서는 프레임을 뽑습니다. SigLIP가 시각 특징을 만들고, 픽셀 셔플이 그 특징의 공간을 채널 쪽으로 접은 뒤, MLP가 그 토큰을 SmolLM2의 입력 차원으로 보냅니다. 시각 토큰은 텍스트 임베딩과 이어 붙여 언어 모델에 들어가고, 나오는 것은 텍스트입니다.

256M config.json이 그 경로에 숫자를 붙입니다.

항목 값 읽는 법
비전 hidden_size 768, patch_size 16, image_size 512, use_base_siglip true SigLIP 베이스. 한 변 512를 16으로 나누면 32칸, 패치 1,024개
압축 scale_factor 4, pixel_shuffle_factor 4 논문의 셔플 비율 r. 토큰 수는 r²=16으로 줄어 타일당 64개
리샘플러 use_resampler false Perceiver 설정 블록은 파일에 남아 있으나 꺼져 있다
텍스트 hidden 576, 30층, 헤드 9, KV 헤드 3, FFN 1536, vocab 49,280 SmolLM2-135M 쪽 디코더. GQA
위치 max_position_embeddings 8192, rope_theta 100000 체크포인트의 값. 논문 2.2절이 적은 실험은 RoPE base를 10k에서 273k로 올린 것이고, 이 파일의 100000과는 다른 수이다
이미지 입력 do_image_splitting true, 긴 변 2048, 타일 긴 변 512 논문의 분할. 고해상도 이미지와 축소본을 같이 넣는다
비디오 입력 fps 1, max_frames 64, 긴 변 512 현재 preprocessor_config.json의 video_sampling

픽셀 셔플은 초해상도에서 온 space-to-depth입니다. 논문은 Idefics3와 InternVL이 r=2를 쓰는 반면, 작은 VLM은 r=4가 이득이었다고 적습니다. 토큰이 줄면 어텐션 비용이 줄고, 대신 한 토큰이 더 넓은 영역을 덮어 OCR처럼 위치가 중요한 작업은 손해라고 같은 절이 적습니다.

비디오 쪽 선택은 평균을 내지 않는 것입니다. 논문 그림 3의 오른쪽은 프레임을 2장, 4장, 8장씩 평균낼수록 OpenCompass-Video가 떨어진다고 보여주고, 그래서 평균을 최종 설계에서 뺐다고 합니다. 각 프레임은 인코더 해상도로 줄여 따로 넣습니다. 카드의 학습 데이터 문장은 SmolVLM2가 10개 데이터셋에서 온 330만 샘플을 썼다고 하고, 모달리티 비율은 이미지 34.4%, 텍스트 20.2%, 비디오 33.0%, 다중 이미지 12.3%입니다. 논문 4.1절의 비디오 파인튜닝 단계도 비디오 비율을 33%로 적습니다.

프레임이 긴 변 512의 타일 한 장으로 끝나면, 프레임당 64토큰입니다. 상한 64프레임이면 시각 토큰은 4,096개이고, 컨텍스트 8,192 안에 텍스트를 더할 자리가 남습니다. 이 4,096은 설정값으로 곱한 계산이고, 프로세서가 프레임을 더 나누는 경우는 따로 재지 않았습니다. 논문은 평가에서 256M과 500M의 이미지 긴 변을 1,920으로 맞춘다고 적으므로, 카드의 입력 상한 2,048과 평가 해상도는 같은 수가 아닙니다.

시각 구간은 텍스트 표식으로 감쌉니다. 논문은 이미지 앞에 "Here is an image…", 비디오 앞에 "Here are N frames sampled from a video…" 같은 문을 두고, 뒤에서 다시 지시문으로 돌아온다고 합니다. 이 표식이 비디오에서 이득이 컸다고 같은 절이 적습니다.

카드의 점수, 논문의 메모리

256M 카드의 비디오 표는 이렇고, 논문 Table 1의 256M 열과 세 칸이 같습니다.

크기 Video-MME MLVU MVBench 카드가 적은 비디오 추론 GPU RAM
2.2B 52.1 55.2 46.27 5.2GB
500M 42.2 47.3 39.73 1.8GB
256M 33.7 40.6 32.7 1.38GB

논문 표의 MVBench는 500M 39.7, 2.2B 46.3으로 카드보다 소수 한 자리가 짧습니다. 256M의 32.7은 양쪽이 같습니다. 논문은 같은 표에 InternVL2-2B를 Video-MME 45.0, MLVU 48.2, MVBench 60.2로 적습니다. 256M은 그 세 칸 모두 아래입니다. 2.2B는 Video-MME와 MLVU에서 그 비교 모델을 앞서고 MVBench에서는 뒤집니다. 카드와 논문 모두 Video-MME의 자막 유무를 이 표에 적지 않습니다.

메모리는 출처가 둘입니다.

  • 논문 Table 1의 RAM, 배치 1: 256M 0.8GB, 500M 1.2GB, 2.2B 4.9GB. 배치 64는 15.0GB, 16.0GB, 49.9GB. 4절 목록은 256M이 1GB 미만의 GRAM에서 돈다고 적고, 본문은 이 열을 단일 이미지 추론이라고 부릅니다. 초록의 "less than 1GB GPU memory"도 이 256M을 가리킵니다.
  • 비디오 카드의 1.38GB, 500M 카드의 1.8GB, 2.2B 카드의 5.2GB는 "video inference"라는 말만 있고, GPU, dtype, 프레임 수, 해상도, 배치가 없습니다. 256M 문장은 "Despite its compact size, requiring only 1.38GB of GPU RAM for video inference."에서 문장이 끝납니다.

F32 가중치만 1.026GB입니다. 카드의 예제 코드는 torch.bfloat16으로 올리므로, 그 경로의 가중치 바이트는 파라미터 수의 2배인 약 0.513GB입니다. 1.38GB는 그 둘 중 어느 쪽과도 같지 않습니다. 1.38이라는 수가 어느 실행의 피크인지는 카드 밖으로 나가지 않습니다.

논문 4.4절은 처리량도 적습니다. A100에서 256M은 배치 1의 초당 0.8예시에서 배치 64의 16.3예시로 늘고, L4에서는 배치 8에서 초당 2.7예시가 정점이었다고 합니다. 같은 절은 256M ONNX를 WebGPU로 14인치 MacBook Pro(M4 Max)에서 디코드 초당 최대 80토큰까지 돌렸다고 적습니다. 이 글은 그 측정을 다시 하지 않았습니다.

코드: transformers, 그리고 문서에 있는 MLX와 llama.cpp

아래는 256M 카드의 비디오 추론 예입니다. 카드는 num2words, flash-attn, 최신 transformers, 그리고 비디오용 decord를 요구합니다. 2025-02-20 블로그는 당시 설치 대상으로 transformers의 v4.49.0-SmolVLM-2 브랜치를 적었습니다. 지금 카드는 "latest transformers"라고 적습니다. 저는 이 코드를 실행하지 않았습니다.

from transformers import AutoProcessor, AutoModelForImageTextToText
import torch

model_path = "HuggingFaceTB/SmolVLM2-256M-Video-Instruct"
processor = AutoProcessor.from_pretrained(model_path)
model = AutoModelForImageTextToText.from_pretrained(
    model_path,
    torch_dtype=torch.bfloat16,
    _attn_implementation="flash_attention_2",
).to("cuda")

messages = [
    {
        "role": "user",
        "content": [
            {"type": "video", "path": "path_to_video.mp4"},
            {"type": "text", "text": "Describe this video in detail"},
        ],
    },
]

inputs = processor.apply_chat_template(
    messages,
    add_generation_prompt=True,
    tokenize=True,
    return_dict=True,
    return_tensors="pt",
).to(model.device, dtype=torch.bfloat16)

generated_ids = model.generate(**inputs, do_sample=False, max_new_tokens=64)
print(processor.batch_decode(generated_ids, skip_special_tokens=True)[0])

이미지와 다중 이미지도 같은 content 리스트에 {"type": "image", "url": ...}를 넣어 카드가 보여 줍니다. 카드의 Uses 절은 텍스트와 미디어를 섞을 수 있고, 이미지 생성과 비디오 생성은 지원하지 않는다고 적습니다. pipeline_tag는 image-text-to-text입니다.

MLX는 블로그가 공개일부터 된다고 적은 경로입니다. 블로그에 실제로 적힌 명령은 256M이 아니라 양자화하지 않은 500M입니다.

pip install git+https://github.com/pcuenca/mlx-vlm.git@smolvlm

python -m mlx_vlm.smolvlm_video_generate \
  --model mlx-community/SmolVLM2-500M-Video-Instruct-mlx \
  --system "Focus only on describing the key dramatic action or notable event occurring in this video segment. Skip general context or scene-setting details unless they are crucial to understanding the main action." \
  --prompt "What is happening in this video?" \
  --video /path/to/clip.mov

블로그는 시스템 프롬프트가 비디오 설명의 길이를 바꾼다고 적습니다. 설치 대상이 smolvlm 브랜치인 것은 2025-02-20 글의 내용이고, 그 글의 댓글은 당시 transformers도 그 시점의 브랜치가 필요했다고 적습니다. 2026-11의 mlx-vlm 메인이 이 모델을 그대로 받는지는 확인하지 않았습니다.

llama.cpp 쪽 1차 자료는 두 곳입니다. ggml-org/llama.cpp#13050은 SmolVLM2-256M-Video-Instruct를 지원 목록에 넣으며 "input sequence of images"라고 적고, 시험 명령으로 llama-mtmd-cli -hf ggml-org/SmolVLM2-256M-Video-Instruct-GGUF를 적습니다. 2026-11에 연 GGUF 카드의 실행 예는 다음 한 줄이고, 비디오 파일 인자는 없습니다.

llama serve -hf ggml-org/SmolVLM2-256M-Video-Instruct-GGUF

GGUF 카드는 Apache 2.0, base_model은 위의 Hugging Face 체크포인트, 변환은 ggml-org의 자동 변환이라고 적습니다. transformers 경로만 decord로 mp4를 받는 예가 카드에 있습니다.

파인튜닝 링크는 2.2B 카드가 smollm의 노트북을 가리킵니다. 블로그는 500M을 Colab에서 전부 파인튜닝하는 편이 낫고, 2.2B에는 QLoRA를 시도해 볼 수 있다고 적습니다.

한계

  • 카드의 언어는 영어입니다. 한국어 화면의 글자를 읽어 한국어로 해설하는 용도는 카드가 적은 언어 밖에 있습니다.
  • 논문이 작은 모델에 r=4를 고른 이유는 토큰 절약이고, 같은 문단이 OCR과 위치 정밀도 손상을 적습니다. 작은 글씨가 많은 게임 HUD는 그 손해가 해당되는 자리입니다. 게임 HUD를 이 모델로 재지는 않았습니다.
  • 카드의 오용 목록에는 개인에 대한 평가, 자동화된 중대 결정, 사실처럼 보이는 부정확한 내용, 그리고 무단 감시가 있습니다.
  • 블로그가 256M에 붙인 말은 실험입니다. 아이폰 로컬 데모와 VLC 연동 문장은 500M과 가족 전체를 가리키고, 하이라이트 데모는 축구 경기를 시험했다고 적습니다.

비즈니스 인사이트

점수 차이가 곧 제품의 자리이다 (분석)

같은 가족 안에서 Video-MME는 256M 33.7, 500M 42.2, 2.2B 52.1입니다. 블로그는 500M이 파라미터 4분의 1 미만으로 2.2B와 같은 비디오 이해를 얻는다고 적습니다. 이름의 500/2200은 0.23이고, 실제 개수 507,482,304 / 2,246,784,880도 0.226이라 "4분의 1 미만"은 맞습니다. 42.2와 52.1이 같다는 문장과는 표가 다릅니다. 의견으로는, 용량을 먼저 자르는 제품은 500M을 보고, 256M은 그 다음으로 더 자를 때의 실험 자리입니다. 블로그가 256M에 적은 기대도 특수 목적 파인튜닝입니다.

논문 표의 InternVL2-2B(Video-MME 45.0, MLVU 48.2, MVBench 60.2)보다 256M이 낮은 것은, 이 모델의 주장이 정확도 1위가 아니라 메모리라는 뜻으로 읽는 편이 표와 맞습니다. 논문은 Qwen2-VL-2B의 평가 RAM을 13.7GB, InternVL2-2B를 10.5GB로 적고, 256M의 배치 1 RAM을 0.8GB로 적습니다. 이 RAM은 논문의 이미지 평가 설정입니다.

다른 회사의 작은 모델과 나란히 놓으면 자리의 차이가 더 분명합니다. 아래 수는 서로 다른 프로토콜이라 순위표가 아닙니다.

Qwen2.5-VL-3B의 3,754,622,976은 256,484,928의 14.6배입니다. 자막 없는 Video-MME 61.5와 SmolVLM2의 33.7은 평가 조건이 같아 확인된 비교가 아닙니다. 자릿수가 다르다는 것까지가 두 문서를 나란히 읽어 말할 수 있는 범위입니다. Qwen 저장소의 연구 라이선스는 상업 배포 전에 따로 허가를 받는 구조이고, SmolVLM2 카드는 Apache 2.0입니다. 의견으로는, 점수가 아니라 배포 조건 때문에 256M을 집는 팀이 이 표에서 설명되는 팀에 가깝습니다.

Gemma 3의 270M과 1B는 시작 문서 기준으로 텍스트 모델입니다. 이미지를 받는 가장 작은 Gemma 3는 4B입니다. Gemma 3n E2B는 비디오 입력을 카드에 적지만, 문서의 유효 파라미터 1.91B를 256,484,928로 나누면 7.4배이고 표준 실행은 50억을 넘긴다고 같은 문서가 적습니다. 2025-03-12 Gemma 3 블로그는 이미지, 텍스트, 짧은 비디오를 한 문장에 적고, 그 문장의 각주는 4B, 12B, 27B가 비전을 지원한다고 적습니다. 모델 카드의 입력 목록은 이미지입니다.

Moondream의 2024-12-05 글은 0.5B를 "the world's smallest Vision-Language Model"이라고 부릅니다. 그 문장의 대상은 이미지 VLM이고, 0.5B는 256M보다 큽니다. 논문이 비교하는 Moondream2는 2~3B 대로, ChartQA 72.2, MMMU 29.3, VRAM 3.9GB입니다. 0.5B 발표와 논문의 Moondream2는 다른 세대입니다.

더 작은 비디오-텍스트 모델이 없는 것은 아닙니다. MobileViCLIP 논문은 모바일용 비디오-텍스트 검색과 제로샷 분류 모델을 다루고, 생성해서 문장을 쓰는 언어 모델이라고 부르지 않습니다. 256M보다 작은 생성형 비디오 언어 모델을 이번 조사의 1차 자료에서 확인하지는 못했습니다. 그것이 2026-11 기준으로 존재하지 않는다는 증명은 아닙니다.

누가 이득을 보나 (분석)

  • 자기 화면을 기기 안에서 짧게 설명해야 하는 팀. 가중치 파일이 1.026GB이고 라이선스가 Apache 2.0입니다. 클라우드에 프레임을 보내지 않는 구성이 성립합니다. 논문의 WebGPU 문장(M4 Max, 디코드 초당 최대 80토큰)은 그 구성이 브라우저까지 내려가 본 기록입니다.
  • 도메인 파인튜닝을 할 팀. 256M 카드가 이 크기를 두는 이유로 적은 것이 제한된 자원에서의 특수 목적 파인튜닝입니다. 일반 비디오 점수는 가족 안에서 가장 낮습니다.
  • 한국어 제품, 자막 없는 장시간 영상, 게임 HUD의 작은 글씨. 카드의 언어는 영어이고, 샘플링 상한은 1fps에 64프레임이며, r=4는 논문이 OCR에 불리하다고 적은 설정입니다. 이 세 조건이 제품의 본업이면 표의 이득이 작습니다.

게임 화면 해설은 세 번째가 아니라 두 번째에 가깝습니다. 자기 게임의 화면을 이미지로 넣어 영어로 설명하는 프로토타입은 카드가 허용하는 입력과 출력 안에 있습니다. 그것을 미니 도우미 기능으로 측정한 자료는 카드, 블로그, 논문에 없습니다.

비용 (분석과 의견)

클라우드 API 단가는 이 모델에 없습니다. 비용은 상주 메모리와 놓치는 정확도입니다.

분석: 배치 1의 0.8GB는 논문의 단일 이미지 열입니다. 카드의 1.38GB는 조건이 없는 비디오 문장입니다. 배치를 64로 올리면 논문의 256M도 15.0GB입니다. "작은 모델이라 항상 1GB 근처"는 배치 1에서만 논문과 만납니다. 항상 켜 두는 카메라나 화면 캡처는 프레임을 쌓는 순간 카드가 적지 않은 쪽으로 메모리가 움직입니다. 상한 64프레임, 프레임당 64토큰이라는 위의 계산은 그 상한이 4,096시각 토큰이라는 뜻이지, 그 길이의 VRAM을 제가 재었다는 뜻은 아닙니다.

의견: 256M을 고르는 이유는 33.7로 61.5짜리 모델을 대체하기 위해서가 아닙니다. 상업 라이선스가 막혀 있거나, 프레임이 기기 밖에 나가면 안 되거나, 틀린 설명 한 줄을 나중에 큰 모델이 다시 보는 초안이면 자리가 있습니다. 그 초안을 사실로 사용자에게 보여 주는 제품은 카드가 적은 오용(사실처럼 보이는 부정확한 내용)과 겹칩니다.
